<h2 align="center">Featured projects</h2>

<details open>
<summary><b>TakaTrail</b> · Multi-user personal finance app</summary>

<br/>

A multi-user desktop app for tracking income and expenses, setting monthly budgets, and viewing reports and charts.

| Dimension | Details |
|:--|:--|
| **Stack** | Java 17 · Swing · Maven · SQLite / JDBC · JFreeChart |
| **Scale** | Multi-user accounts. Each user's transactions, budgets, reports, and exports stay isolated. |
| **Performance** | Local SQLite storage with no network calls. Dashboard totals and six-month trends compute on demand. |
| **Security** | PBKDF2WithHmacSHA256 hashing with a random salt per user. Every query is scoped to the signed-in user. |
| **Impact** | Passed 31 of 31 functional smoke checks and 10 of 10 UI checks. I built the GUI, domain model, dashboard, reports, integration, and tests in a team of three. |
| **Repository** | [![TakaTrail](https://img.shields.io/badge/GitHub-TakaTrail-7C3AED?style=flat-square&logo=github&logoColor=white&labelColor=0D1117)](https://github.com/moon-drakon/TakaTrail) |

An abstract `Transaction` class defines the shared contract. `Income` and `Expense` extend it and run through `Transaction` references at runtime. Sign-in gates every screen, and budget overruns trigger warnings. A written verification record covers user isolation, persistence, backup and restore, and validation.

</details>

<details>
<summary><b>Wealthora</b> · Offline-first finance suite</summary>

<br/>

An offline-first finance suite for accounts, transfers, budgets, recurring entries, savings goals, loans, and debts.

| Dimension | Details |
|:--|:--|
| **Stack** | Java 25 · Swing · Java2D · Apache Ant · BCrypt · GitHub Actions |
| **Scale** | 2.3 MB+ of Java across 10 packages, per-user CSV workspaces, and a separate OTP relay service |
| **Performance** | Runs fully offline: finance, reports, import, export, and recovery. Writes use safe file replacement, and one process owns the data folder. |
| **Security** | BCrypt for passwords and recovery answers. Email OTP goes through a separate relay, so the app stores no SMTP secrets. OWNER, ADMIN, and USER roles with an audit log. |
| **Impact** | CI on GitHub Actions. PDF and CSV export, validated CSV and Money Manager import, offline voice entry, and light and dark themes. |
| **Repository** | [![Wealthora](https://img.shields.io/badge/GitHub-Wealthora-6366F1?style=flat-square&logo=github&logoColor=white&labelColor=0D1117)](https://github.com/moon-drakon/Wealthora) |

Data flows one way: `Swing UI → Service → Model → Repository → CSV`. The UI never touches storage. Services validate and coordinate, and repositories persist. Interfaces wrap export, speech recognition, and OTP delivery, so each one can change on its own. No finance data leaves the device.

</details>

<details>
<summary><b>NSU Blood Donor &amp; Emergency Request System</b> · Emergency donor matching in C</summary>

<br/>

A role-based system that matches blood donors to emergency requests and tracks each donation until it is verified.

| Dimension | Details |
|:--|:--|
| **Stack** | C · structs · binary file I/O (`fread` / `fwrite`) · modular functions |
| **Scale** | Three roles: admin, donor, and requester. Ships with 139 approved donors and 73 emergency requests for demos. |
| **Performance** | Fixed-layout binary records. Request status is recalculated from assignments and verified blood bags. |
| **Security** | Admin approval for new donors, PIN-based request tracking, two-step donation sign-off, and an activity log that records who did what. |
| **Impact** | Covers the full emergency flow: blood-group matching, multiple and backup donors, donor replacement, and text reports. |
| **Repository** | [![Blood Donor System](https://img.shields.io/badge/GitHub-Blood%20Donor%20System-4F46E5?style=flat-square&logo=github&logoColor=white&labelColor=0D1117)](https://github.com/moon-drakon/blood-donor-emergency-request-system) |

Requests and assignments move through defined states, from pending to fulfilled and verified. Every input is validated. A donation is final only after the requester confirms it and an admin verifies it. Records live in binary files, and reports and logs export as plain text.

</details>
